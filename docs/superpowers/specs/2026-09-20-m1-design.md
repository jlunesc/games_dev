# M1 Design: player, arena, fixed loop, hit feedback

Approved by the owner in chat on 2026-09-20, section by section. Implements milestone M1 of `docs/SPEC.md` section 11. Controller facts come from `docs/controllers.md`.

## Decisions taken for M1
- **Arena (LOCKED):** one fixed screen, side view, flat floor and walls, no camera movement.
- **Scaling (LOCKED):** fixed 16:9 world of 1280 by 720 game units, scaled to the largest size that fits, with dark bars where the screen is wider.
- **Content (owner's choice):** a throwaway training dummy that can be hit and swings back after a visible warning. Replaced by the Ember Duelist in M2.
- **Feel (DELEGATED):** Hollow Knight-like starting values, all tunable in one data file. Variable jump height, no coyote time (no late-jump forgiveness), input buffer of 3 updates.
- **Dash (LOCKED):** short fixed cooldown, about 0.4 seconds after the dash ends, tunable.
- **Structure (LOCKED):** one plain state object advanced by a pure `step(state, input)` function at 60 updates per second.
- **Settings (owner's choice):** the on/off settings object and the settings screen both arrive in M3 with the menu. In M1 everything is simply on.
- **DEFAULT (approved in review):** pause when the controller disconnects; a clear message for controllers with a non-standard layout and no profile; a small start screen.

## Architecture
```
gamepad -> input profile -> InputFrame (one per update)
                                 |
fixed loop (60 updates/s) -> step(state, input) -> new state + events
                                 |-> renderer (Canvas 2D, interpolated between updates)
                                 |-> freeze (held by the loop, not part of the state)
                                 |-> feedback (shake, flashes) and sound, driven by events
```
- `step` never reads a clock, random numbers, the DOM or the gamepad. Given the same starting state and the same inputs it always gives the same result.
- **Freeze on impact is held by the loop driver, not by `step`.** When a hit event arrives, the loop stops running updates for a few updates' worth of real time. The simulation therefore counts the same number of updates whether the freeze is on or off, so reaction times in the stats are unaffected and switching the freeze off never changes how a fight plays. Presses made during a freeze are kept by the input buffer.
- Time in stats is counted in updates (1 update = 16.7 ms).
- Effects (shake, flashes) and sound are driven by the events `step` emits (`playerHit`, `dummyHit`, `dash`, `dummyWindup`, `playerDefeated`, and so on). They never write to the state.

## Modules
| File | Responsibility |
|---|---|
| `src/engine/loop.ts` | Pure `planUpdates(leftoverMs, frameMs)` returning how many updates to run, the new leftover and the blend factor, capped at 5 updates per frame; plus a thin `requestAnimationFrame` driver that also holds the freeze. |
| `src/engine/input-profile.ts` | `ControllerProfile` (physical buttons to actions), the SN30 Pro profile, the standard profile, `selectProfile(id, mapping)`, and `sampleInput(...)` producing an `InputFrame` with dead zone applied. |
| `src/game/params.ts` | All tunable values (world, player, dummy, feedback) as data. |
| `src/game/state.ts` | State and event types, `createInitialState()`. |
| `src/game/step.ts` | `step(state, input)` and small helpers for the player and dummy state machines and collisions. |
| `src/ui/render.ts` | Draws the state on a canvas in the fixed world, letterboxed, blended between updates. |
| `src/ui/feedback.ts` | Shake and flash amounts computed from events and the update count. |
| `src/ui/audio.ts` | Three short sounds generated in code (hit, dash, warning). Unlocked by the first button press, as browsers require. |
| `src/ui/app.ts` | Switches between start screen, fight and controller test; disconnect and unsupported-controller messages. |

The controller test screen from M0 stays, reached from the start screen, with an on-screen Back button.

## InputFrame and controls
`InputFrame`: `moveX` (-1 to 1 after the dead zone), `jumpHeld`, `jumpPressed`, `attackPressed`, `dashPressed`, plus menu actions `confirm` (bottom button) and `alt` (top button).
- **SN30 Pro profile** (id `8Bitdo SN30 Pro (STANDARD GAMEPAD Vendor: 045e Product: 02e0)`): bottom = button 0 (jump, confirm), left = button 3 (attack), top = button 4 (alt), right shoulder = button 9 (dash), d-pad = 12 to 15, left stick = axes 0 and 1. Buttons 6 and 7 and the right stick are ignored entirely, because 6 and 7 read about 0.5 at rest.
- **Standard profile** (used only when the browser reports `mapping: standard` and no specific profile matches, for example the PC pad): bottom = 0, left = 2, top = 3, right shoulder = 5, d-pad 12 to 15, left stick axes 0 and 1.
- Profiles are matched on the controller's full id text. The same pad under another browser or system can report a different id and then falls back to the standard profile (if the browser reports a standard layout) or to the message below. New ids get new profiles from controller test reports.
- A controller with a non-standard layout and no profile shows its name and a message pointing to the controller test screen. The game does not guess.
- Stick dead zone starts at 0.25, tunable. The d-pad and stick both move the player.
- Disconnect mid-fight pauses; reconnecting and pressing a button resumes.

## Player and dummy: starting values (first guesses, DELEGATED, tunable)
World 1280 by 720 units; the floor is a flat line near the bottom. Times in seconds convert to updates at 60 per second.

| Value | Start |
|---|---|
| Player size | 48 wide, 96 tall |
| Run speed | 420 units/s (same speed in the air) |
| Gravity | 2600 units/s squared; max fall speed 1100 units/s |
| Jump | launch speed 900 units/s (about 155 units high if held by the continuous formula; 163.33 at the fixed timestep); releasing early while rising cuts the upward speed to 40% |
| Attack | 3 updates start-up, 4 updates active, 9 updates recovery; hits a box 90 wide and 80 tall in front; usable in the air; moving during it at half speed |
| Dash | 11 updates (about 0.18 s) at 1450 units/s (about 265 units), horizontal only, gravity paused, invulnerable throughout; cooldown 24 updates (0.4 s) after it ends; usable in the air |
| Health | 5 hits; after a hit, 60 updates (1 s) untouchable; no knockback |
| Input buffer | 3 updates for jump, attack and dash; no coyote time |
| Dummy | 96 wide, 160 tall, stands at about x = 960; hit points only for display, refills, never dies |
| Dummy sweep | first sweep 2 s after the fight starts, then every 3 s; 30 updates of warning (color change and pull-back), 8 updates active, 24 updates recovery; hits a low box 120 tall that reaches 220 units out from the dummy's edge and covers the dummy's near half, so standing inside the dummy is not a safe spot; it can still be jumped over or dashed through; 1 hit of damage |
| Defeat | at 0 health, 60 updates later the arena restarts (the real death flow arrives with the menu in M3) |

`step` order each update: apply buffered inputs, update the player, apply movement and gravity, update the dummy, resolve attack and sweep collisions, emit events, update timers.

## Hit feedback (from SPEC section 8, all on in M1)
- Freeze: 4 updates when the player hits the dummy, 8 when the player is hurt.
- Shake: about 6 units, fading over 10 updates.
- Flash: dummy turns white for 6 updates when hit; the player flashes red when hurt and blinks during the untouchable second.
- Sound: hit, dash and dummy warning beeps generated in code.

## Tests
- **Automated (Vitest):**
  - `step`: jump duration and height, early release cut, dash length and exact invulnerability, cooldown of exactly 24 updates, one hit cannot hit twice, dummy sweep starts and lands on the expected update, jumping over and dashing through the sweep, defeat and restart, determinism (same inputs give identical state).
  - `planUpdates`: whole updates from elapsed time, the 5-update cap, the blend factor.
  - Input profiles: both profiles turn the right buttons into the right actions, buttons 6 and 7 are ignored on the SN30 Pro profile, the dead zone, `selectProfile` for known, standard and unknown controllers.
- **Manual (owner):** a checklist in `docs/phone-testing.md` covering movement feel, dash, attack range, the dummy's warning, taking a hit, the effects, pause on disconnect, and play on the PC pad and the S21. Feel values are tuned from the owner's feedback.

## Out of scope for M1
Boss data format and the Ember Duelist (M2), the counter mechanic, the menu, the settings screen, the summary screen, stats logging and export (M3), knockback, healing, extra moves, platforms, sound beyond three effects, music, touch and keyboard controls.

## Done when
Tests pass, CI is green and deployed, the owner has played it on the PC pad and the S21, and any feel changes they asked for are made.
