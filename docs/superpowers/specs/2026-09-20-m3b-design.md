# M3b Design: recording fights, storing them, exporting them

Second step of M3 (the outline is in `docs/superpowers/specs/2026-09-20-m3-design.md`, approved by the owner on 2026-09-20; the export choice, the share sheet or a saved file and never an upload, is **LOCKED** by the owner). Everything below is **DELEGATED** detail: what is recorded, how it is stored and how the screens work. The owner found on 2026-09-20 that M3a shows no export option, which is expected: this step adds it.

## The idea: record the inputs, measure by replay
The game is deterministic. A fight is fully described by the boss id, the difficulty dials, the seed and the input given to each update. So the game records only that (small and exact), and a pure **analyzer** replays the fight through the real `step` to produce every measurement of SPEC section 9 (per attack, per fight, behavior). Consequences: measurements can be added or corrected later from old fights without playing again; the recorder cannot disagree with the game; and a fight can be watched again later if a replay viewer is ever built.

A record is only replayable with the same game version (attack timings and player numbers are in the code and boss file), so each record carries `gameVersion` and the analysis is stored with it when the fight ends.

## Pieces
- **Input log** (`src/stats/input-log.ts`): the input frame given to each update that ran (not to frozen updates), stored as runs: `[frame, count]` where `frame` packs `moveX` (-1, 0, 1 as two bits), `jumpHeld`, `jumpPressed`, `attackPressed`, `dashPressed` into one small integer, and `count` is how many updates in a row it repeated. `moveY`, `confirm` and `alt` are not part of a fight and are not stored. Encode and decode are exact inverses.
- **Recorder** (`src/stats/recorder.ts`): pure. `startRecording(meta)` returns a recording; `recordUpdate(recording, frame)` adds one update's input; `finishRecording(recording, result, tickAtEnd)` gives the raw part of a record. The app calls it next to `step`, exactly where the fight flow is fed (`fight-flow.ts`), so a fight is recorded from its first update to the update it ends or is left.
- **Analyzer** (`src/stats/analyze.ts`): pure. `analyzeFight(raw): Analysis` replays with `createInitialState`, `applyDials(bossById(...))` and `step`, and reads the states and events. It never changes the game.
- **Record** (`src/stats/record.ts`): `FightRecord` = `{ schemaVersion, gameVersion, id, playedAt (ISO date), attempt, bossId, dials, changedDials, presetId, seed, result, ticks, input (runs), analysis }`. `schemaVersion` is 1 and is documented in `docs/stats.md`; any change to the shape bumps it and the doc.
- **Storage** (`src/stats/store.ts`): an interface `FightStore { add(record), all(), clear(), count(), nextAttempt() }` with an in-memory version for tests and an **IndexedDB** version for the browser (database `boss-trainer`, store `fights`, key `id`). Every call is guarded: if IndexedDB is unavailable or fails, the game still plays and the Stats screen says the device cannot store stats. Nothing leaves the device.
- **Export** (`src/stats/export.ts`): `buildExport(records, now)` returns the export document (`{ format: 'boss-trainer-stats', schemaVersion, exportedAt, gameVersion, fights: [...] }`) and a file name like `boss-trainer-stats-2026-09-21.json`. `shareOrDownload(file)` uses the Web Share API with a file where the browser supports it (the phone's share sheet), and otherwise a normal file download. It is the only browser-only piece and is kept tiny.
- **Stats screen** (`src/ui/stats-model.ts` pure, plus rendering in `screens.ts`): a menu row "Stats" opens it. It shows how many fights are saved, the date of the last export, a reminder that Android can clear browser data so export regularly, and the rows "Export", "Delete all fights" (asks again before deleting) and "Back". Navigation as elsewhere.
- **Wiring** in `app.ts`: recording starts with the fight and finishes at the same moments a summary is produced (win, loss, leaving); a fight left before any update ran (`tick === 0`) is not stored. The record is analyzed and saved when the fight ends; a failure to save shows a small notice on the summary, never blocks the game.

## What the analysis contains (SPEC section 9, all measured in updates and also in ms)
Times are in updates (1 update = 16.7 ms, hit-freeze not counted); the export also gives `ms` values (`updates * 1000 / 60`) so the file reads easily.
- **Fight:** result, ticks, phase reached, boss hp left and max, damage dealt (boss hp lost), damage taken (player hp lost), hits taken, the hit timeline (tick of each hit on the boss and each hit on the player), swings made and swings that hit (accuracy), counters landed, dashes, jumps.
- **Per boss attack occurrence:** attack id, phase, start tick (when the warning began), windup ticks, first dangerous tick, distance to the player when it began, the player's facing and action when it began, and:
  - `outcome`: `hit`, `countered` or `dodged`.
  - `evasion` (when dodged): `dash`, `jump` or `distance` (the player was simply out of reach).
  - `reactionTicks`: from the start of the warning to the player's first dash or jump before the dangerous moment (null if none).
  - `marginTicks` (dodged by dash or jump): first dangerous tick minus the tick the dodge began, so a small number means a late, tight dodge; for a `hit` where the player dashed or jumped too late, the same number is negative.
  - `damageTaken`, and `playerAction` when hit (`idle`, `running`, `airborne`, `dashing`, `attacking`).
- **Behavior:** counts per action, player x sampled once per 6 updates (10 per second), updates spent close (distance under 160), mid (160 to 400) and far (over 400), and punish windows: after each boss attack ends (recovery) the window opens; it is `taken` when the player hits the boss in it and `missed` otherwise; `greedy` when the player swings and gets hit in the window.
- Derived measures (learning curve, fatigue, hit rate per attack across attempts) are not stored; they are computed afterwards from many exports.

Any field the analyzer cannot measure exactly is null, never a guess.

## Testing
Input log: encode then decode gives back the same frames for random and edge sequences; runs merge correctly. Recorder: a played fight and a replay from its record reach the same final state (the key determinism test, using the real `step` and boss with a scripted input). Analyzer: scripted fights with known outcomes (a dodge by dash, a dodge by jump, a hit, a counter, a whiff by distance) give the expected outcome, reaction and margin; totals agree with the M3a summary numbers for the same fight; the same record analyzed twice is identical. Store: the memory store round-trips, clear and count work; the IndexedDB store is exercised only through its interface in the browser (manual check). Export: document shape, schema version, file name, and that a record survives JSON round trip and still replays to the same result. Stats model: focus, delete asks twice. Manual (owner): checklist in `docs/phone-testing.md`, including exporting on the phone and sending the file.

## Out of scope
CSV export, a replay viewer, charts inside the app (analysis happens with Claude on the exported file), cloud sync, and any upload.

## Done when
Tests pass, CI is green and deployed, and the owner has played several fights on the phone, exported the file through the share sheet, and the exported file replays and analyses correctly (checked by Claude on the real file).
